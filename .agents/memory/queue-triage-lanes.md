# Queue triage lanes & red-reserved policy

**Rule:** Every queue item carries a server-stamped `lane` (`ready` | `action` | `monitor`) and a required `whyText` (plain-English evidence). Lanes: ready = pickup pipeline; action = a human must fix something (9 location/record problems, 4 auth stuck, 7 with replacement, and step 2 Scheduling); monitor = watch-only (8 PO/date inference, 5 LUCA retry cadence, 6 paperwork). Monitor renders collapsed by default on both queue UIs. **Lanes are NOT step-shaped guarantees** (verified live 2026-08-10): step 1/3 → ready but step 2 (Scheduling) → action, and lane `ready` contains rows WITHOUT phone confirmation (escalated/confirm-returned rows). Any "confirmed ready" membership decision must gate on evidence (`readyReason` 'luca'|'manual'), never on lane or step shape alone.

**Red is reserved** for real urgency only: overdue SLA, status conflicts, Totaled/Repair Declined. A closed/paid Holman PO is billing paperwork, NOT evidence the truck needs pickup — those rows are neutral monitor, never red. Contact-failure LUCA labels (No Answer, No Shop Contact, Call Failed) are amber retry states, not red.

**Why:** User directive (Aug 2026): the board was "all red", closed-PO rows implied false pickup urgency, and LUCA escalations needing human action (wrong phone, shop says truck isn't there) fell invisibly through step 5's badStatus filter into noAction. Step 9 ("Verify truck location / shop record") now claims those labels (Shop Does Not Have Truck, Relocated, No Shop Contact, Needs Tow, Unverified) plus workbook `escalated` cases.

**Step-9 evidence-aware disposition (2026-08-06):** step-9 lane/copy comes from ONE pure module (`evaluateStep9Disposition` in shop-record-flags). 'No Shop Contact' is LUCA's `shop_contact_missing` escalation (callDerived:false — it never dialed; its feed row had no usable phone), persisted on `fs_trucks.last_call_status` while the card chip is the LIVE reconciled pick — so the old copy could contradict its own card once the record improved. Demotion to monitor requires HARD evidence only: 'No Shop Contact' → the reconciled pick carries a dialable phone (the fs_trucks fallback phone is NOT LUCA-dialable and never demotes; that copy must not cite a call date — the escalation stamps none). 'Shop Does Not Have Truck'/'Relocated' → dispatch-provenance mismatch (dialed name/phone vs pick, BOTH sides present; missing values never flag; a newer PO date alone never demotes). 'Needs Tow'/'Unverified' never demote.

**How to apply:** New queue steps/rows MUST set lane + whyText (TS-required on the server QueueItem type — don't make them optional there). Don't route location-problem LUCA labels back into step 5. Both UIs (VRM OpsQueue inline-styles + FS TodaysQueue Tailwind mirror) must stay in lane-parity; lane banners expose `data-testid="lane-*"` and `aria-expanded` for testability.

## Dead fs_trucks fields must not be read as evidence (2026-08-10)
- The step-2 self-conflict check originally treated `fs_trucks.repair_completed = false` as contradicting a live LUCA Ready call. Removed per user: since VRM became rental authority (2026-08-04), that flag is a dead FS-era field — the Rental Ops mirror sync never writes it, FS rental edits are locked, and mirror-created rows sit at the column DEFAULT false forever (345/357 rows false, 14/15 Scheduling trucks; even the original "13 of 21 false" measurement that justified the check was this artifact).
- **Why:** a schema default is not a record; pitting it against live phone evidence produced bogus "resolve the contradiction" warnings on genuinely ready trucks.
- **How to apply:** before using ANY fs_trucks field as queue/VRM evidence, confirm the Rental Ops mirror sync (or another live writer) actually maintains it — if only legacy FS-era surfaces wrote it, treat it as dead. The surviving self-conflict leg (sub-status claims "Scheduled, awaiting tech pickup" but scheduled_pickup_date is null) is valid because both sides are actively maintained.

## Scheduling-validation gate & AMS terminal override (added 2026-08-07)
- A truck whose shop status reads "Scheduling" must NEVER present as pickup-ready on its own: without validation (LUCA call history or a manual verify mark) it buckets as `scheduling_unvalidated`, not a pickup lane. `schedule_tech_pickup` requires `confirmedReady`.
- AMS declined/auction is TERMINAL and overrides shop-status classification entirely — such trucks bucket by the action actually needed (e.g. `ams_status_conflict`), never by pickup readiness.
- **Why:** "Scheduling" from the portal routinely means "shop answered the phone once", not "van is ready"; and a declined/auctioned van must not be dispatched to.

## Terminal-truck needs_replacement bucket — policy reversal (2026-08-10)
- Terminal trucks (declined/auction FS status incl. 'Approved for sale', or AMS-terminal) with NO replacement assigned are now a first-class workable bucket (`needs_replacement` — locate a spare) instead of classify() returning `[]` → "No action". Deliberate reversal of the earlier "sourcing is not this queue's job" ruling, per user directive.
- Semantics: P1 but `slaBusinessDays: null` (availability-driven work — no red overdue nag), owner regional, pushed AFTER `retrieval_pending` so retrieval stays primary on decommission rows; lane monitor unless classifications are exactly `[needs_replacement]` AND spares exist → action. Only remaining `[]` dead-end: terminal + replacement assigned + that replacement itself in the shop.
- Work-type bucket = server-stamped `workBucket` per item (claim rules in `workBucketForItem`, unit-tested): primary `needs_replacement` → locate-a-spare pile; else lane `ready` + `readyReason` luca/manual + no terminal-family classification (needs_replacement/retrieval_pending/replacement_assigned/ams_status_conflict) → `vehicle_ready_schedule`; else primary (`'other'` safety). Rollup counts and BOTH UIs group off this field — never recompute membership client-side. Net effect: the Ready pile = exactly the phone-confirmed set even when a paperwork/scheduling sub-state outranks it as primary. Spare decoration is a raced non-blocking lookup — an absent `spareAvailability` means "lookup unavailable", never zero spares.
- Side effect to expect: AMS-terminal rows that used to surface primary `ams_status_conflict` now surface primary `needs_replacement` (conflict stays as a secondary pill) — a small conflict bucket is not a regression.
- **Layout lesson (round-2 rework, 2026-08-10):** shipping the buckets as a filter strip over the existing P1–P4 priority board was rejected — the new P1 classification (~100 rows) flooded the P1 section and the board "looked like just filters". A bucket that changes volume needs a LAYOUT answer, not only a filter: both surfaces now default to bucket-SECTION boards (one labeled pile per `workBucket`, Ready pinned first with its confidence line, needs-replacement second, step→priority sort inside; strip chip = focus one section; OpsQueue keeps By-person + Step-board views, FS keeps a Steps toggle).
