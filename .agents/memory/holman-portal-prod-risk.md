---
name: Holman portal (playwright) production risks
description: Non-obvious deploy risks for the VRM Holman rental-PO awaiting-auth feature (headless Chromium + live financial writes).
---

The VRM "Holman rental PO awaiting-authorization" feature logs into insights.holman.com with a **real headless Chromium** (`playwright-core`) to harvest a JS-gated session, then runs approve/deny postbacks over HTTP. Two durable, non-obvious deploy hazards:

- **Chromium presence is not guaranteed in the autoscale image.** `playwright-core` ships NO browser binaries. It works in dev only because dev's `/nix/store` happens to contain a `playwright-chromium-cjk-…-1187` build and `HOLMAN_CHROMIUM_PATH` is pinned to a `/nix/store/...` path. But neither `.replit` (`[nix] packages`) nor `replit.nix` declares a Chromium/playwright-browser nix package, and `npm run build` runs no `playwright install`. So in a published autoscale deploy the pinned path / `/nix/store` scan can resolve to nothing → `chromium.launch()` fails → the whole Holman PO feature is dead (refresh, approve, deny). It is on-demand only (route `/api/vrm/holman-po-queue/*`), NOT a boot-time call, so the app still boots — only this feature breaks. The headless login also runs in an ISOLATED child process (`holman-login-worker.ts`) so a Chromium crash/OOM/hang cannot take down Express.
  **How to apply:** to make this survive publish, declare the playwright chromium as a real nix package (so it's baked into the deploy image) OR provision it at build time, and verify `HOLMAN_CHROMIUM_PATH` + `HOLMAN_PORTAL_USER`/`PASS` exist in the DEPLOYMENT env (secrets are per-environment, not inherited from dev).

- **Live Holman writes are gated by a single inverted env flag.** `dryRun = process.env.HOLMAN_DECISION_DRY_RUN !== "false"` — i.e. writes are simulated UNLESS the var is the exact string `"false"`. The public `approvePoInHolman`/`denyPoInHolman` default `dryRun=true`, but the route passes the env-derived value. When `HOLMAN_DECISION_DRY_RUN=false`, Approve/Deny perform REAL postbacks (actual rental-PO approvals/declines = money) against Holman production. There is also `HOLMAN_DECISION_DISABLED=true` as a hard kill-switch. Routes are session-gated (`requireAuth`) but approve/deny only require a `decidedByName` string in the body — no RBAC role check, so any authenticated session can commit a real Holman decision.
  **Why:** publishing with `HOLMAN_DECISION_DRY_RUN=false` arms live financial actions; the first Approve/Deny click is real. Confirm intent + the flag's value in the deployment specifically, and consider an RBAC gate.
