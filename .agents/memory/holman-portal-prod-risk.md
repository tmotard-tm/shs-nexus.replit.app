---
name: Holman portal (playwright) production risks
description: Non-obvious deploy risks for the VRM Holman rental-PO awaiting-auth feature (headless Chromium + live financial writes).
---

The VRM "Holman rental PO awaiting-authorization" feature logs into insights.holman.com with a **real headless Chromium** (`playwright-core`) to harvest a JS-gated session, then runs approve/deny postbacks over HTTP. Two durable, non-obvious deploy hazards:

- **Chromium presence is not guaranteed in the autoscale image — FIXED by declaring a top-level nix browser package.** `playwright-core` ships NO browser binaries. Dev only worked because dev's `/nix/store` had ORPHANED, undeclared `playwright-chromium…` builds and `HOLMAN_CHROMIUM_PATH` pinned to one of them. The deploy image is built ONLY from declared nix config, which declared no Chromium, so prod logged `chromium=auto` then 502'd ("Executable doesn't exist … chromium-1097"). The feature is on-demand (`/api/vrm/holman-po-queue/*`), not boot-time, so the app still boots — only this feature broke. Headless login runs in an ISOLATED child process (`holman-login-worker.ts`) so a Chromium crash can't take down Express.
  **Fix that worked:** `installSystemDependencies(["ungoogled-chromium"])` → adds `pkgs.ungoogled-chromium` to `replit.nix` deps, so the binary + its full runtime closure is baked into the deploy image. `resolveChromiumPath()` step 4 auto-finds `/nix/store/…-ungoogled-chromium-<ver>/bin/chromium` (regex `ungoogled-chromium-[0-9]`, excludes `sandbox$`) — no secret/code change needed. In prod, steps 1–3 fall through (pinned dev path absent, no playwright builds in the clean image) so step 4 wins.
  **Why ungoogled-chromium and not playwright-driver.browsers (architect's 1st choice):** the dotted attr `playwright-driver.browsers` is NOT in the package tool's rippkgs index (`NIX_PACKAGE_UNAVAILABLE`), and hand-editing `replit.nix`/`.replit` is BLOCKED by tooling — so only TOP-LEVEL rippkgs attrs are installable. `ungoogled-chromium` is top-level, was already cached in `/nix/store`, and is the SAME Chromium 125.0.6422.141 build family as `playwright-driver.browsers` (both smoke-tested OK under `playwright-core@1.41.2`: launch + `page.evaluate`). Plain `playwright-driver` is useless here — its default output has no browser.
  **How to apply / gotchas:** confirm post-publish that prod logs show `chromium=/nix/store/…-ungoogled-chromium…/bin/chromium`, NOT `chromium=auto`. Step 4 does not sort multiple ungoogled matches (fine in a clean image; only one declared version present). `HOLMAN_CHROMIUM_PATH`/`HOLMAN_PORTAL_USER`/`PASS` are global Secrets (apply in prod) — the pinned path just doesn't exist in the image, which is why step 1 correctly skips. Only a real post-publish Approve/Refresh test confirms it end-to-end.

- **Live Holman writes are gated by a single inverted env flag.** `dryRun = process.env.HOLMAN_DECISION_DRY_RUN !== "false"` — i.e. writes are simulated UNLESS the var is the exact string `"false"`. The public `approvePoInHolman`/`denyPoInHolman` default `dryRun=true`, but the route passes the env-derived value. When `HOLMAN_DECISION_DRY_RUN=false`, Approve/Deny perform REAL postbacks (actual rental-PO approvals/declines = money) against Holman production. There is also `HOLMAN_DECISION_DISABLED=true` as a hard kill-switch.
  **Why:** publishing with `HOLMAN_DECISION_DRY_RUN=false` arms live financial actions; the first Approve/Deny click is real. **It is stored as a Replit Secret, and Secrets are GLOBAL (not environment-scoped)** — so the same value applies to BOTH dev and the deployment; there is no separate prod value to set. (Note: Replit env *vars* CAN be scoped shared/development/production, but Secrets cannot.) Confirmed set to `false`. Changing a Secret after deploying requires a republish to take effect.

- **Access to the whole feature is restricted to a named-username allowlist (NOT a role).** All four routes (`GET /holman-po-queue`, `POST .../refresh`, `POST .../:id/approve`, `POST .../:id/deny`) are gated by `requireHolmanApprover` in `server/vrm/routes.ts`, allowing only the usernames in `HOLMAN_APPROVER_USERNAMES` (currently Tyler Morgan = `jmorga1`, Rob Anderson = `handers`); everyone else gets 403. The client (`NewRentals.tsx`) mirrors the same allowlist (`canApproveHolman`) to hide the section and skip the GET so other VRM users don't 403. **Why username and not role:** the two approvers have different roles (developer vs admin), so a role check can't express the set. **Keep it VRM-contained** — do NOT promote this to global `role_permissions`/RBAC or copy the allowlist into other modules; to change who can approve, edit the one Set in `server/vrm/routes.ts` (and the mirror in `NewRentals.tsx`).

- **A client visibility gate keyed only off the real session leaks under the developer "preview as user/role" (mirror) feature.** `canApproveHolman` originally used `useAuth().user.username`, so while developer `jmorga1` mirrored a NON-approver the restricted section stayed visible. **Rule:** any username/role-gated UI must compute its *effective* identity from `usePreviewRole()` — `previewUser ? previewUser.username : previewRole ? "" : real username` (role-only preview has no username → fail closed). **Why:** the preview feature is exactly how a developer "mirrors" another user's view; the server stays safe (`req.user` is unchanged by preview), but the UI must reflect the previewed identity. **Second, subtler trap:** `PreviewRoleProvider` must hydrate preview state SYNCHRONOUSLY (useState lazy-init reading sessionStorage), not in a `useEffect` — effect-hydration leaves preview null on the first render after a reload, so the restricted section flashes (and fires its query) as the real developer before the preview takes over.
