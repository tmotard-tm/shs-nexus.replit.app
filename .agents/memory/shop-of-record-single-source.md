---
name: Shop-of-record single source
description: Every VRM surface showing "current shop"/phone must use the server-reconciled pick, never re-derive client-side
---

**Rule:** Any UI that shows a rental case's current repair shop or its phone must anchor on the server-reconciled shop-of-record (the SHOP_PICK-based context also served to the queue and board table, exposed to drawers as `reconciledShop` with its backing `poNumber`). Never re-derive a "current shop" client-side from raw PO history, and never prefer a per-PO scraped phone over the reconciled/global number.

**Why:** The board table used portal-corrected effective statuses + the global verified phone while the case drawers re-picked from raw ETL `poStatus` and showed per-PO scraped phones — operators saw different shops/numbers on the table vs. the drawer and couldn't tell which one LUCA dialed.

**How to apply:** New surfaces read `reconciledShop` (or `loadQueuePoContext()`, which is SWR-cached and ~free). Phone precedence: manual/locked > Pep Boys directory (store-number-exact) > same-vendor per-PO scrape > directory zip/city match > name-matched global scrape — never a truck-level portal phone belonging to a different vendor. LUCA dispatch provenance (shop actually dialed) lives in `vrm_rental_operations_call_log` rows with `source='luca_dispatch'`; the table stays empty until dispatches log, so all dialed-shop chips must degrade to nothing, and mismatch flags must never fire on missing values.

**Pick rule (Tyler ruling 2026-08-05 — RESOLVED the old SHOP_PICK vs SHOP_STRICT divergence):** the shop of record is the most recent eligible repair PO **by date, regardless of PO status** (the APPROVED-first board ordering is retired), and a towing/recovery/roadside/glass/TRAC-named vendor may **never** be the shop of record even when Tyler's parts/labor exception counts its PO as an open repair (that exception still governs open counts/callability — the ban applies only at the pick). The rule lives in one place (`NEVER_SHOP_RE` + a sync-tested SQL twin in vendor-class) and is applied in the pick CTEs AND the portal-side event picker; keep JS/SQL patterns in lockstep via the parity unit test.

**Pep Boys phones:** the operator-supplied store directory (boot-seeded, value-guarded upsert — deploys run no migrations) is authoritative for Pep Boys numbers; portal scrapes carry placeholder junk (222-222-2222) and wrong-vendor numbers, so scraped phones are only usable when name-keyed to the picked vendor.

**Junk-phone gate (Tyler 2026-08-05 — "never show 2222222222"):** the stored portal phone is cleaned (cleanPhone) at the master row-mapping BEFORE callable/call_* fields are computed — board, region view, and CSV exports all inherit it; queue context and LUCA feed were already clean. A boot heal nulls legacy junk/unusable shop_phone values (unlocked rows only) so the precedence chain takes over — without it the stored junk survives the sticky-valid no-op compare forever. Client drawers must junk-gate any RAW scrape fallback (per-PO vendorPhone, portal shop phone).

**Phone stickiness (Tyler 2026-08-05 — "numbers stay accurate without re-scraping daily"):** manual phone edits LOCK BY DEFAULT (server: omitted `locked` = true when a number is provided, explicit false honored, clearing unlocks; client toggles auto-enable on a changed number until deliberately unticked). The scrape write path has a sticky-valid guard: a stored USABLE number (10 clean digits, non-repeated) is never replaced by nothing/junk — only by another valid number, a manual edit, or the episode-end lock expiry. Explicit unlock = consent for valid scrape corrections only.

**Boards display the pick too (2026-08-06):** `/master` and `/by-region` attach `reconciledShop` per LIST row (same SWR PO-context the queue reads); the boards' shop cell renders its phone and falls back to the raw portal phone ONLY when the field is ABSENT (pre-ship cached response or PO-context load failure — the routes OMIT the field on failure; stamping `reconciledShop:null` would read as "authoritatively no pick" and blank every phone on the board). Portal number present but pick phone null → "no verified phone" + set-aside tooltip; the edit pencil still seeds the RAW portal phone (it edits the override layer). The dispatch-provenance map is keyed NAMESPACED — `truck:<canon>` / `case:<canon>` (pure `buildLucaDispatchMap` + collision tests): one mixed key space let a case key digit-identical to a different truck's number shadow that truck's dispatch = false provenance = wrongful step-9 demotion.

**Manual shop-NAME override (2026-08-05):** operators can correct the shop of record in place (queue popout panel → `/master/:truck/shop-info`). Name and phone have deliberately DIFFERENT semantics: the phone shares one column with the scraper and needs `locked` to stick; the name lives in its own `shop_name_override` column that scrapes never write, so it wins by presence (readers `COALESCE(override, pick)` in SQL/JS — queue context, board master, region view, LUCA feed all coalesce the same column and cannot disagree). Both expire on the same episode-scoped board clock (`expireStaleShopPhoneLocks`, ~7-day grace after the case leaves the board). Gotcha: an override name breaks the vendor-name-keyed scrape-phone checks by design (a renamed shop's old scraped phone must not survive), so a name edit should normally come with a phone edit — the panel sends only changed fields to avoid materializing the PO pick into an override.
