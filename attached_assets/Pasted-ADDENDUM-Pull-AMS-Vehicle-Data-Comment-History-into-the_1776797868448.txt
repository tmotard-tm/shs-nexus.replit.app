ADDENDUM — Pull AMS Vehicle Data & Comment History into the Rental Repair Tracker
Source: The AMS side panel visible on /fleet-management when a vehicle is selected. It contains two relevant sections:

AMS Information — Ownership (AMS Tech, TFD, DSM, TM), Description (Color, Branding, Interior, AMS Odometer, Book Value, Lease End, Reg Renewal, Lifetime Maint., Storage Cost), Condition (Road Ready, Grade + grade description, Truck Status, Theft Verified, How Vehicle Runs, How Vehicle Looks), Location (Delivery Location, Delivered date), and an "AMS last updated" timestamp with updater.
AMS Comments / History — A timestamped, author-tagged log (authors seen: AMSAUTO, SYSFIX, mismatch, individual user IDs like cgroce, rchadn0). Entries include tech reassignments, registration mailings, renewal date changes, user field updates, and free-text operational notes. Count indicator in the header (e.g., "AMS Comments / History (79)").

Goal: Every Rental Repair Tracker row should display the matching vehicle's AMS snapshot and full AMS comment history inline, matched by truck number, without the user leaving the tracker page.

1. Matching key

Primary match: truck_number on the rental repair tracker row → truck_number on the fleet/AMS record. Exact string match, case-insensitive, with leading zeros preserved (e.g., 036207 must not match 36207 unless the fleet record stores it the same way — confirm in the DB before normalizing).
Fallback match: VIN, if truck # is null on either side.
If multiple fleet records match (shouldn't happen, but possible with decommissioned/reissued numbers): prefer the record whose truck_status is not Out of Service and whose AMS last-updated timestamp is most recent. Log a warning in the changelog output if a collision occurs.
No match found: show "No AMS record for truck #XXXXXX" in place of the AMS panel, and surface a link_missing flag on the row so admins can investigate.

2. UI integration on the Rental Repair Tracker
Add an AMS drawer to each row, opened either by:

Clicking the truck number cell (replace the current behavior so the truck # is the primary entry point), OR
A new chevron/expander at the left edge of the row that slides the row open into a two-panel detail view.

The drawer renders on the right side of the tracker page (same page, not a new route) and mirrors the fleet-management side panel exactly, with three sections stacked:
Section A — AMS Snapshot (read-only)
Render every field from AMS Information in the same grouping and labels as the fleet page:

Ownership: AMS Tech, TFD, DSM, TM
Description: Color, Branding, Interior, AMS Odometer (with as-of date), Book Value, Lease End, Reg Renewal, Lifetime Maint., Storage Cost
Condition: Road Ready, Grade + grade description, Truck Status, Theft Verified, How Vehicle Runs, How Vehicle Looks
Location: Delivery Location, Delivered date
Footer: "AMS last updated: {timestamp} by {updater}"
A View in Fleet Management link that opens the full fleet page for that vehicle in a new tab (deep link by VIN or truck #).

Section B — AMS Comments / History (read-only from tracker, full fidelity)

Full timeline, newest first, with header count matching the source (e.g., "AMS Comments / History (79)").
Each entry renders: author badge (color-coded by type — AMSAUTO / SYSFIX / mismatch system tags get one style, human user IDs get another), timestamp (local time, with UTC on hover), and the comment body.
Search-within-comments box at the top of the section.
Filter chips: System only, Humans only, Tech changes, Registration/Renewal, Free text. (Derive categories by regex on the comment body; if classification is ambiguous, default to Free text.)
Virtualize the list — some vehicles have 79+ entries and we don't want to render them all at once.

Section C — Tracker Notes (writeable, already specified in main prompt)
This is the Tech Outreach + Shop Contact Log two-timeline component. It stays on the tracker side of the drawer. Do not write tracker notes back to AMS. Do not modify AMS comments from this page — all writes to AMS happen on the fleet page through the existing Add Comment button.
3. Data fetching strategy

On tracker page load, batch-fetch the AMS snapshots for every truck # currently rendered in Action Needed + In Progress sections. Do not prefetch Completed/Archived — lazy-load when expanded.
On drawer open, fetch the full AMS Comments history for that truck #. Cache per-truck in memory for the session; invalidate on manual Refresh AMS click or when the 15-minute sync job runs.
Reuse the same API endpoint that powers the fleet-management side panel. Do not duplicate backend logic — expose a shared service/controller (e.g., amsVehicleService.getByTruckNumber(truck_number) and amsCommentService.listByTruckNumber(truck_number, {limit, offset})) and call it from both the fleet page and the tracker drawer.
If the AMS fetch fails, show a small inline error with a retry button. Do not block the rest of the row from rendering.

4. Column-level surface (at-a-glance, without opening the drawer)
Even with the drawer, some AMS signals are valuable enough to surface directly on the collapsed row. Add as subtle indicators on the truck # cell:

Truck Status icon (green dot for Assigned to Tech, gray for Spare, red for Out of Service).
AMS Odometer (small muted text under the truck #).
⚠ icon if Road Ready = No or How Vehicle Runs indicates non-operational.
Tooltip on hover: "AMS last updated {relative time}".

Do not clutter the main grid beyond this — everything else belongs in the drawer.
5. Search and cross-section behavior

Extend the existing tracker search box so a query also matches against AMS fields: VIN, license plate, AMS Tech name, Delivery Location city/state, and the body of the most recent 10 AMS comments. Matches in AMS fields should still return the tracker row (since the tracker row is the unit of display), with a small "matched in AMS: {field}" badge.
When a row is expanded, its AMS drawer respects the same filter chips that are active at the tracker level (e.g., if you filter to one district, the drawer only opens for rows in that district — nothing changes there, but make sure opening a drawer doesn't clear the page filter state).

6. Refresh and staleness

The drawer shows "AMS data as of {timestamp}" at the top of Section A.
A Refresh AMS button in the drawer header does a live fetch for that one truck, bypassing the cache.
Global Sync Now button at the page level should also refresh AMS snapshots for all currently visible rows.

7. Permissions and privacy

AMS snapshot + comments are read-only in the tracker. No write-back path.
If the current user lacks permission to view the AMS record (e.g., cross-region restriction), show "AMS record exists but you do not have access" rather than the full panel. Preserve existing fleet-management ACLs — do not widen access via the tracker.

8. Acceptance criteria (additions to the main prompt's §11)

Expanding the row for truck # 036207 (Muhammad Bilal Wali) loads an AMS drawer showing the same Ownership / Description / Condition / Location / Comments data that appears when the same truck is opened from /fleet-management.
Comment counts match between the fleet page and the tracker drawer for at least five sample trucks.
A truck # that doesn't exist in AMS renders the row normally with a "No AMS record" inline notice and a link_missing flag.
Editing an AMS comment from the fleet page and returning to the tracker + clicking Refresh AMS on that row shows the updated comment without a full page reload.
No additional writes hit the AMS system from the tracker — verify via network trace that only GET requests go to AMS endpoints from /vehicle-rental-management/rental-repair-tracker.
Drawer open time for a vehicle with 79 comments is under 500 ms on cached sessions and under 1.5 s on cold fetch.

9. Deliverables (additions)

Document the shared service/controller used by both fleet-management and the tracker drawer.
Include a list of any AMS fields that could not be surfaced (with reason) so we can decide whether to prioritize them in a follow-up.
