## Review structure

Produce a clearly structured report. For each section below, adopt the stated perspective and maintain it throughout that section. Label every finding as Critical, High, or Low severity.

### Perspectives
1. End User / UX — evaluate the experience from the perspective of someone using the app day-to-day: ease of use, clarity, friction points, emotional response, task completion, and first-run experience.

2. Manager / Product Owner — assess business value delivery, feature completeness vs. user goals, reporting and visibility, operational risk, and whether the product is solving the right problem.

3. Senior Full-Stack Developer — review code quality, architecture patterns, testability, dependency hygiene, security practices, API design, database schema and query efficiency, deployment setup, and technical debt.

4. Security Reviewer — identify authentication/authorization gaps, injection vulnerabilities, data exposure risks, insecure dependencies, and missing security headers or controls.

5. Performance Engineer — identify bottlenecks, unnecessary re-renders or queries, caching opportunities, bundle size issues, and anything impacting perceived or actual load times.

6. Accessibility Auditor — evaluate WCAG compliance, keyboard navigability, screen reader compatibility, colour contrast, and accessible form labeling.

## Pre-mortem
Imagine it is 18 months from now and the application has failed or caused serious problems. Work backward. What were the most likely causes? Consider:
- Technical failure modes (scaling, data loss, outages)
- Product failure modes (users abandon it, core use case unmet)
- Operational failure modes (team can't maintain or evolve it)
- Security or compliance incidents
Rank each by likelihood and impact.
