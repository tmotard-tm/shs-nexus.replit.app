Pre-Deployment Data-Loss Audit + Guardrails (Read-Only First)
Goal: Diagnose exactly why past Replit publishes of this app have lost data, then install lightweight guardrails that protect against recurrence without slowing anyone down. No code changes, no migrations, no deploy actions during the diagnosis phase. Guardrails only get built after the user approves the diagnosis.
Phase 1 — Diagnosis (read-only, no writes)
Run all of the following and produce a single report titled PRE-DEPLOY-DATA-LOSS-DIAGNOSIS.md in .local/tasks/. Do not modify any file outside that directory.
1. Environment and DB wiring

Print the effective DATABASE_URL host, database name, and branch name (not the password) for:

Local development environment (what npm run dev uses)
Deployed autoscale environment (what the production bundle connects to)


Are they the same database? Same branch? If Neon, list every branch that exists in this Neon project and which branch each environment targets.
Check for any .env, .env.production, .env.local, .env.development files and report which DATABASE_URL they set. Flag any mismatch.
Confirm whether the deployment uses Replit Secrets vs. committed env files for DATABASE_URL. If Secrets, note when each was last changed if that metadata is available.

2. Build and start script inspection

Read package.json and report the exact contents of scripts.build, scripts.start, scripts.postinstall, scripts.predeploy, and any other script that runs during deploy.
Inspect the .replit config's [deployment] block (already confirmed as build = ["npm", "run", "build"] / run = ["npm", "run", "start"]) — walk every command in those scripts transitively.
Flag any command that includes: drizzle-kit push, drizzle-kit generate, db:push, db:reset, db:seed, prisma migrate deploy, prisma db push, TRUNCATE, DROP, rm -rf, or any shell redirect into a DB URL. Report the command, the file it's in, and the line number.
Specifically grep the entire repo for drizzle-kit invocations and list every shell script, package script, or CI file that calls it.

3. Migration runner behavior

Does this app run migrations on boot (in server/index.ts or equivalent)? Show the code path.
Is there a pending-migration runner that executes any drizzle/ or migrations/ file on cold start? If yes, list every migration file that has not been applied to production's DB.
For each unapplied migration, grep the file for DROP, TRUNCATE, ALTER TABLE ... DROP COLUMN, ALTER TABLE ... RENAME, or any destructive DDL. Classify each migration as safe or destructive and explain why.
Special focus: this session added schema changes for the repair tracker (new columns, two new timeline tables, deprecation of last_action writes). List every Drizzle schema diff relative to live production DB. Does Drizzle's current db:push behavior in this repo use --safe? Report the exact command.

4. Seed / fixture scripts

Grep for any .sql or .ts file whose name or contents suggests seeding, resetting, or fixtures.
For each one: is it wired into any lifecycle hook (build, start, postinstall, deploy)? If it writes to a DB that matches the production DATABASE_URL, flag it as a data-loss risk.

5. Evidence of prior loss events

Check sync_logs, activity_logs, operation_events, or any audit-style table for patterns around prior deploys where row counts dropped dramatically.
Cross-reference with any Replit deployment history you can read.
For each VRM-related table (vrm_repair_tracker, vrm_tech_notes, vrm_shop_contact_log, vrm_new_rental_log, vrm_rental_decisions, vrm_outreach_log, etc.), report current row count and any field that tracks row-level created_at / updated_at gaps that would suggest rows disappeared and got re-seeded.

6. Neon branch reset risk (if applicable)

If this project uses Neon: report the branch topology. Identify whether the dev branch is configured to auto-reset from prod (or vice versa) on any event. Report the "Branch reset on" setting for every branch if accessible.

7. External integrations that could wipe data

List every fs_* importer (approved_cost, fleet_cost, PO, PMF, registration) and report whether any of them use TRUNCATE + INSERT patterns vs. upserts. Flag any importer that wipes a table before loading.
Same check for the AMS sync job, the Holman sync, and the Snowflake punch-status sync.

Output format
Write findings as a single markdown doc with these sections:

A. Root-cause ranking — your best guess at what caused past data loss, with evidence, ranked most-likely to least-likely.
B. Active risks for this specific pending deploy — what would happen if the user hits Publish right now? Any destructive migration pending? Any table the new build would reseed?
C. Evidence table — one row per command/script/migration you inspected, with file path, line, and safe/risky verdict.
D. Recommended guardrails — the minimum set of protective steps for Phase 2, designed to run automatically without user friction.

End the report with the line: DIAGNOSIS COMPLETE — AWAITING GUARDRAIL APPROVAL.
Do not proceed to Phase 2 until the user replies GUARDRAILS APPROVED — BUILD.
Phase 2 — Guardrail installation (only after approval, minimum-invasive)
The goal is zero extra friction on normal publishes, but a hard stop if something destructive is about to happen.

Automatic pre-deploy snapshot (silent). Add a pre-deploy hook that, before any build step runs, takes a row-count snapshot of every table in the production DB and writes it to a timestamped file in an S3-equivalent or local backups/ directory (exact storage TBD based on what's available). This runs in under 5 seconds for a DB this size. Fire-and-forget; no user prompt. If the snapshot fails, the deploy continues (never block on telemetry) but a warning is logged.
Migration safety gate (blocking only on destructive ops). Add a pre-deploy script that does a dry-run of any pending migrations and greps the generated SQL for DROP TABLE, DROP COLUMN, TRUNCATE, RENAME on tables with data, or ALTER COLUMN ... NOT NULL without a default on a populated column. If found, the deploy script fails with a clear message: "Destructive migration detected: [file]. Override with --i-know-what-im-doing." Non-destructive migrations pass silently. This is the single guardrail that would have caught every past incident.
Post-deploy integrity check (automatic, silent on success). After the new bundle is live, compare row counts in every tracked table against the pre-deploy snapshot. If any table lost >10% of rows, log an alert to .local/alerts/ and — if email or webhook is configured — send a notification. The deploy is not rolled back automatically (that would create its own class of problem), but the alert lands within seconds.
One-click rollback artifact. On every successful deploy, persist the previous bundle hash, the pre-deploy snapshot reference, and the migration list to a deploys/history.json file. A npm run rollback script that pulls the prior bundle and skips the pending migrations should exist and be documented. Not invoked automatically — it's a break-glass tool.
No UI changes, no developer workflow changes. None of the above adds steps for the user. Publish still works the same way. The guardrails fire on the deploy pipeline, not in the IDE.

Out of scope for Phase 2

Rewriting migration history.
Changing the ORM.
Moving off Replit autoscale.
Any backfill or data recovery from past incidents (those are separate tickets if they come up).

Hard rules across both phases

No code changes during Phase 1.
No migrations run during either phase unless the user explicitly asks.
No db:push, no db:reset, no seed scripts executed during either phase.
If anything in Phase 1 can't be determined from read-only inspection (e.g., Neon branch history without API access), mark it UNKNOWN — requires [specific credential or action] and move on.
Phase 2 guardrails must not add latency to normal deploys beyond 10 seconds total.

Reply format

After Phase 1: post the report and the DIAGNOSIS COMPLETE — AWAITING GUARDRAIL APPROVAL line.
After Phase 2: post a short changelog of what was installed, confirm the next deploy will be protected, and wait for the user to hit Publish.
