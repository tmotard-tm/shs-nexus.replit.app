Two bugs in the Rental Repair Tracker:
Bug 1: PATCH route resets dismissed to false on every save.
The Zod schema generated from insertVrmRepairTrackerSchema.partial() includes dismissed: false as a default. Even when the frontend doesn't send dismissed in the payload, Zod fills it in with false. This means every time a user saves changes on a tracker entry, it silently un-dismisses it.
Fix: In the PATCH /api/vrm/repair-tracker/:id route handler in server/vrm/routes.ts, after parsing the body with Zod, explicitly destructure dismissed out of the parsed data so it can never be set via PATCH:
typescriptconst parsed = insertVrmRepairTrackerSchema.partial().safeParse(req.body);
if (!parsed.success) return res.status(400).json({ error: parsed.error.flatten() });
const { dismissed, ...rest } = parsed.data;
const row = await updateRepairTrackerEntry(req.params.id, rest);
The dismissed field can ONLY be set via the soft-delete endpoint, never via PATCH.
Bug 2: Dismissed rows are being lost during the import dedup, causing re-imports.
Despite the cleanup steps having WHERE dismissed IS NOT TRUE guards, dismissed rows are somehow being removed before the dedup query runs. The fix is to capture the dismissed row IDs BEFORE any cleanup steps run, then merge them into the dedup check.
Fix: In importDeniedToRepairTracker() in server/vrm/storage.ts, at the very TOP of the function (before Step 1's cleanup DELETE), add a query that captures all currently-dismissed source_decision_id and tech_ldap values:
typescript// Capture dismissed row identifiers BEFORE any cleanup runs
const dismissedBlockers = await db
  .select({ 
    sourceDecisionId: vrmRepairTracker.sourceDecisionId, 
    techLdap: vrmRepairTracker.techLdap 
  })
  .from(vrmRepairTracker)
  .where(eq(vrmRepairTracker.dismissed, true));

const dismissedDecisionIds = new Set(
  dismissedBlockers.map(r => r.sourceDecisionId).filter(Boolean) as string[]
);
const dismissedTechLdaps = new Set(
  dismissedBlockers.map(r => (r.techLdap ?? "").toUpperCase()).filter(Boolean)
);
Then in Step 4 (the existing dedup query), after building existingDecisionIds and existingTechLdaps, merge in the dismissed sets:
typescript// Merge dismissed blockers into the dedup sets
dismissedDecisionIds.forEach(id => existingDecisionIds.add(id));
dismissedTechLdaps.forEach(ldap => existingTechLdaps.add(ldap));
This guarantees that even if cleanup steps somehow remove dismissed rows, the dedup check still has the IDs cached and will block re-import.
